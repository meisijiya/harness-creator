# 维护模式：显式调用下的更新与优化

harness 不会腐化出声——它只会让代理慢慢失准。所以「什么时候维护」必须是一个**信号**，不是一个习惯。

## 触发

- **用户显式调用**（主路径）：用户要求更新、优化或收敛 harness 时走这里。代理**不自行发起**——边界节与反例黑名单都禁止本技能主动扩范围、主动发起流程。
- **收口触发**（辅路径）：目标仓库的 `AGENTS.md`「会话结束」节写明——若本次会话改过指令文件、`init.sh` 或工作规则，收口时用本技能重新评估一次。它由会话结束例程带出，不额外开一轮。

不要把触发改成「定期」或「每个里程碑」：本技能没有可靠的节拍信号，而靠代理自觉定时＝靠记忆执行＝没有载体。

## 判据只有一条：作用域

| 目标 | 名称 | 作用域 | 落点 |
|---|---|---|---|
| 本会话产出 | 收尾 | `git diff --name-only <会话起始 commit>` ∪ 未跟踪文件 | 按性质归位；本会话的临时材料清掉 |
| 跨会话的 harness 产物 | 优化 | 指令文件、`init.sh`、工作规则本身 | 直接改既有产物；不新建第二份 |

未提供会话起始 ref 时**不假设 `HEAD`**：只有未提交改动算本会话，其余标「无法判定」，不当作陈旧材料处理。

## 步骤

1. **取证**：`node <技能目录>/scripts/validate-harness.mjs --target /path/to/project` 拿三子系统得分与 FAIL 行；需要分享时再上 `run-benchmark.mjs --html`。
2. **列候选改动**：把 FAIL 行翻成可执行改法，并标注作用域。最低分只是**候选**瓶颈——先确认因果再声称因果；并列最低全部列出，不从并列里挑一个。
3. **🔴 CHECKPOINT**：把「将改 / 将删」清单交用户，获批后才动手。删除属危险动作，必须先列「将删 / 将留」并说明理由。
4. **落地**：以改既有文件为主。指令文件已有内容**不重写**——`create-harness.mjs` 只报告缺失章节，合并由代理执行并保留第三方块；新建才走 `--dry-run` → 获批 → 真写。
5. **复验**：重跑一次验证或基准，如实报出仍未闭合的项。

## 不做什么

- 不 prune 历史工单，不做与 harness 无关的全仓审计，不顺手创建骨架或交接文档。
- 不派生条目、验收标准或决策——那是 `to-tickets` 从对齐结论派生的事。
- 不代做工程流程，不为承接方产物指定位置。
- 不复述条数：得分、阈值与关卡清单以脚本运行时打印为准。

## 异常

| 触发条件 | 处理 |
|---|---|
| 候选改动全部判为「不改」 | 如实汇报，这是正常结果；不为了有产出而改动 |
| 指令文件含第三方块（如 `## Agent skills`） | 只报告缺失章节，绝不 `--force`；合并保留现有全部内容 |
| 用户要求「整个仓库都翻一遍」 | 按作用域拆分：harness 产物的优化可以做，与 harness 无关的部分交回用户另起一轮 |
| 审计已满分 | 报「无候选瓶颈」，不改；为刷分堆关键词是反模式 |

## 反例

1. 把最低分当成已确认的因果，直接照改。
2. 未获批就删掉「看起来没用」的材料。
3. 为提分改文字而不改工具——散文不是载体。
4. 顺手重排、清理其他技能产出的文件。
5. 把「收尾」做成全仓审计，或把「优化」缩成只清临时文件。
