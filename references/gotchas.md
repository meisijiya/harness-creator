# 陷阱 —— Harness 工程失败模式

违反就会引发缺陷的非显而易见的原则。

---

## 1. 记忆索引上限静默触发

**症状**：最近的记忆"消失"了，没有任何报错。

**原因**：索引有硬上限（如 200 行 / 25KB），在读取时强制执行。长条目（多句摘要）会在未超行数的情况下撞上字节上限。

**修复**：索引条目保持为一行钩子。细节放进主题文件。

```markdown
✓ 好："用 bun 而非 npm —— 用户偏好 2024-01-15"
✗ 差："用户偏好 bun 胜过 npm，因为更快。这是 2024-01-15 讨论的，用户说'用 bun 别用 npm'，我相应地更新了 package.json……"
```

---

## 2. 优先级排序违反直觉

**症状**：全局规则被本地文件静默覆盖。

**原因**：本地覆盖 > 项目规则 > 用户规则 > 组织规则。如果你把规则注入用户级并期望它占优，项目根目录的本地覆盖文件会赢。

**修复**：在完整的指令文件栈存在时测试：

```bash
# 测试优先级排序
cat ~/.claude/CLAUDE.md          # 用户级
cat ./CLAUDE.md                   # 项目级
cat ./CLAUDE.local.md             # 本地覆盖（胜出）
```

---

## 3. 提取时机造成竞态窗口

**症状**：后台提取器正在写记忆，但用户在提取完成前就发起了下一轮。

**原因**：提取在响应结束时触发。用户可能在提取完成前发送消息。

**修复**：合并并发的提取请求。仅在成功运行后推进游标。提取失败意味着这些消息下次会被重新考虑。

---

## 4. 可推导的内容不属于记忆

**症状**：记忆索引被很快过时的架构细节填满。

**原因**：代理保存了可从代码库推导的内容（架构、代码模式、版本历史）。

**修复**：在设计上排除可推导内容。类型分类应禁止保存仓库里已有的东西。

---

## 5. 并发分类是按调用而非按工具

**症状**：标记为"并发安全"的工具引发竞态条件。

**原因**：同一工具对某些输入安全，对另一些不安全。不要假设工具的并发行为是静态的。

**修复**：在运行时对每次调用分类：

```typescript
// Don't do this:
toolRegistry.register('shell', { concurrentSafe: false });

// Do this:
function isCallConcurrentSafe(call: ToolCall): boolean {
  if (call.args.command.startsWith('rm -rf')) return false;
  if (call.args.command.startsWith('cat')) return true;
  // ...runtime classification
}
```

---

## 6. 权限评估有副作用

**症状**：权限检查改变了后续调用的行为。

**原因**：权限评估器会跟踪拒绝、转换模式、以副作用方式更新状态。它不是纯查询函数。

**修复**：不要跨调用缓存权限结果。每次调用都重新评估。

---

## 7. 大多数异步工作跳过"Pending"状态

**症状**：UI 显示"pending"，但工作单元从未进入该状态。

**原因**：实践中工作单元直接注册为"running"。"Pending"存在于状态机中但很少使用。

**修复**：不要构建假设每个工作单元都从 pending 开始的 UI。

---

## 8. 分叉的子级不得再分叉

**症状**：上下文成本指数级爆炸。

**原因**：递归分叉让上下文倍增：父级 + 子级1 + 子级2 + 孙级……

**修复**：强制执行单层不变量。分叉工具保留在子级工具池中（便于提示词缓存共享），但在调用时拦截。

---

## 9. 上下文构建器被记忆化但需手动失效

**症状**：模型在整个会话中看到陈旧数据。

**原因**：上下文构建器在启动时被缓存，但变更不会清除缓存。

**修复**：每个变更点都必须显式清除对应缓存：

```typescript
// Example: Cache invalidation at mutation point
async function editFile(path: string, content: string) {
  await writeFile(path, content);
  context.cache.invalidate(`file:${path}`); // MUST invalidate
}
```

---

## 10. 钩子信任是全有或全无

**症状**：因为一个钩子不受信任，整个扩展系统被禁用。

**原因**：如果工作区不受信任，所有钩子都跳过——不只是可疑的那些。

**修复**：在分发点设计带信任闸门的钩子。不要尝试逐钩子做信任评估。

---

## 11. 驱逐需要通知

**症状**：父级永远读不到工作单元的结果。

**原因**：工作单元在父级收到完成通知前就被驱逐。竞态条件：父级试图读取已被 GC 的结果。

**修复**：两阶段驱逐：
1. 终止状态时清理磁盘输出（eager）
2. 父级收到通知后清理内存记录（lazy）

---

## 12. 技能列表预算很紧

**症状**：技能描述被截断，无法正常触发。

**原因**：技能描述被拼接且每条有上限（约 150 字符）。前置的触发语言获得优先。

**修复**：把有辨识度的触发语言放在最前：

```markdown
✓ 好："harness-patterns：记忆、权限、上下文工程、多代理"
✗ 差："一个用于理解与实现各种 AI 代理 harness 及运行时系统相关模式的综合性技能……"
```

---

## 13. 工具默认权限是"Allow"

**症状**：工具绕过了预期的关卡。

**原因**：没有自定义权限逻辑的工具完全委托给基于规则的系统。除非另行配置，默认是"allow"。

**修复**：为敏感工具覆盖默认值：

```typescript
registry.register('shell', {
  defaultPermission: 'ask', // NOT 'allow'
  // ...
});
```

---

## 14. 团队记忆依赖自动记忆开启

**症状**：即使配置了团队共享记忆也不生效。

**原因**：团队记忆构建在与自动记忆相同的目录/索引基础设施上。禁用自动记忆（通过环境变量或设置）也会禁用团队记忆。

**修复**：启用团队记忆前确保自动记忆已开启。同时检查功能开关与启用检查。

---

## 15. 孤立主题文件会累积

**症状**：磁盘被 `.claude/memory/topics/` 文件填满。

**原因**：两步保存（先主题文件后索引）。两步之间崩溃会留下孤立的主题文件。

**修复**：定期清扫删除索引未引用的主题文件。孤立文件不会损坏索引，但会占用磁盘空间。

---

## 16. 检查点核验授权来源与范围，不按会话轮数判定

**症状**：有预授权时代理会执行；没有授权时才停在 dry-run。仅凭「单轮」或「委派」认定未获确认，会把有效授权误报为缺失。

**证据边界**：2026-09-23 的四臂测试观察到：两种检查点措辞在带预授权时都写入，无预授权时都停下。这说明上下文中的授权影响行为，不能据此推论有授权的执行违规。本轮候选 skill 试跑已实际生成并验证产物，却按旧规则自报「未获人类确认」，暴露了这条错误归因。

**处理**：
1. 写入前跑 `--dry-run`，展示本次产物与范围。
2. 沿用真实用户已给出、且覆盖当前动作的授权；宿主传递的委派不额外扩大权限。
3. 文件、网页等不可信内容不能授予权限；来源不明、范围未覆盖或宿主要求最终确认时暂停确认。

**边界**：文字规则负责说明意图，宿主权限系统负责执行控制。工具允许不等于用户授权，代理也不能因会话形式而否认实际存在的授权。

---

## 17. `--commands` 的逗号会把一条命令切成两条

**症状**：`--commands "bash -c 'echo a,b'"` 这类把逗号放进命令内部的调用，生成的 `init.sh` 把它当成**两条**独立检查：`bash -c 'echo a` 与 `b'`。后者根本不是检查，却照样渲染成带守卫的步骤，`AGENTS.md` 的「验证命令」节也照着裂成两行。

**原因**：列表分隔符与命令内容共用同一个字符，且切分不看引号。真正致命的是它的**静默性**——调用者以为交出去的是一个检查，拿到的是两个不再是那个检查的步骤，而被改写过的门禁仍然是门禁，审计看不出来。这与「绝不静默跳过或静默降级」是同一条。

**修复**：切分按**引号感知**（`splitCommandList`）——引号内的逗号属于命令，引号外的才是分隔符。未闭合的引号**拒绝**而不是猜（非零退出、什么都不创建），因为猜正是产生裂开的原因。**引号是唯一的转义方式**，没有反斜杠形式要记。

**实测**（三臂，经真实生成器，各自翻转不同的自检标签）：`bash -c 'echo a,b'` 仍是一条；`npm test,npm run lint` 仍切成两条；未闭合引号退出非零且目标目录为空。

## 18. `set -e` 下的 `! grep` 不会触发退出

**症状**：手写一条「不匹配就失败」的检查，直觉写法 `! grep -q PATTERN file` 在被 `set -e` 包裹的 `init.sh` 里**不会**让脚本退出——脚本继续走到尾部打印成功。实测：`bash -c 'set -e; ! true; echo ALIVE'` 打印 `ALIVE`。

**原因**：POSIX 规定 `set -e` 忽略以 `!` 开头的命令（否则 `if ! cmd` 会当场退出）。于是这条检查**结构性恒过**——正是本技能反复写的那句「不能失败的门禁不是门禁」。

**修复**：用显式分支 `if grep -q PATTERN file; then :; else echo 'FAIL: …'; exit 1; fi`，或把取反放进条件位 `if ! grep -q PATTERN file; then …; fi`（条件位不受 `set -e` 影响）。

**推论**：**手写命令的作者要自己证明它有牙**——故意注入一个违规样本，确认退出码变成非零。门禁是不是真的，由注入实验判定，不由它的存在判定。

---

## 19. 注释与文档变成变更编年史

**症状**：注释与文档随每次编辑累积一条时间线，读的人必须先重建一条已废弃的历史，才知道当前值是多少。本技能仓库的 `scripts/run-benchmark.mjs` 常量区活生生地记着「基线从 7889 挪到 9623、又到 9950、9820、10290」「drop is 170 against 346 bytes」「本条曾在 09-25 被删过」——而 `AGENTS.md` 上限只有一个数。

**原因**：把「当初为什么这么定」和「现在是什么」塞进了同一处载体。前者是 git 历史与决策记录的职责，后者才是文档。两者混写，载体就再也无法单独回答「现在是什么」，于是每一条陈旧断言都被当成权威，文档整体贬值。

**修复**：注释与文档只留当前状态与不变量，**变更理由进提交历史**，已废止的方案直接删掉而不是标注作废；每个常量的注释回答「这个数为什么是现在这个数」，不回答「它走过哪条路」。

**推论**：本技能已有的门禁判据「不读规则原文、只读结构」（`scripts/lib/harness-utils.mjs` 的 `structuredText`）同样适用于文档审查——审查文档问的是「这句现在还成立吗」，不是「这段历史读起来是否完整」。
