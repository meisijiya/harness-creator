# 会话收尾（Session wrap-up）

**一句话**：把**本次会话的产出**收敛回状态产物，让下一次会话能立刻重新启动。

作用域是**会话**，不是仓库——收尾只处理本会话新增与改动的部分，不 prune 历史条目、不做全仓审计。

## 触发

用户表达收尾意图时触发。常见说法：「收尾」「结束这次会话」「wrap up」「这次先到这儿」。

- 用户不必说出 "harness" 这个词。
- 触发后**先定界，再动手**——范围没定下来之前不改任何文件。

## 作用域如何确定

- 首选：会话起始 commit。范围 = `git diff --name-only <ref>` ∪ 未跟踪文件。
- 未提供 ref：**不假设 `HEAD`**（HEAD 会把已提交的本会话内容误判为历史）。此时只有「未提交改动」可确定为本次会话，其余标「无法判定」，**不得把「无法判定」当作「本会话」处理**。
- git 不可用：降级为人工列清单，由用户圈定本会话产出。
- 非 git 产出（只在对话里生成、从未落盘的内容）：判断它该不该落盘；不落盘即视为丢弃，一句话说明即可，**不为它专门建文件**。

## 四步流程

### ① 定界

按上节确定本次会话的范围，列出本会话新增与改动的文件。

### ② 归位

逐个判断本会话产出该落在哪里；**同一事实只落一处**：

| 本会话产出的东西 | 落点 |
|---|---|
| 可执行约束（测试、Schema、门禁） | `init.sh` / CI |
| 跨会话有效的**长期不变量** | 目标仓库 `AGENTS.md` 的「工作规则」节——受该节自身条目上限约束：先合并同族项，合并后仍超，就重新判断它能否落进 `init.sh`/CI |
| 状态与依赖 | `feature_list.json` / `progress.md` |
| 业务代码 | 无需「归位」——代码即文档，随提交走 |
| 已无价值的临时草稿 | 清场（③） |

归位 = 写进落点，**引用而不复制**。

### ③ 清场

清掉本会话新增且已无价值的临时材料。

🔴 **CHECKPOINT**：删除前逐条列出「将删 / 将留」并获批准。

**本步不碰**：非本会话文件；历史累积的条目；指令文件（`AGENTS.md`/`CLAUDE.md`）的任何内容。

### ④ 记账与收口

**输入**：本会话推进的功能项；**输出**：状态文件里下一次会话可直接读到的证据。

按目标仓库 `AGENTS.md` 的「会话结束」一节执行——**引用而不复制**。该节缺失时的最小动作：更新 `progress.md`（当前状态、证据、阻塞、下一步）→ 更新 `feature_list.json` 的 `status` 与 `evidence` → 记未解决的风险 → 干净提交。

**完成判据**（缺一即未完成，逐项核对）：

1. `progress.md` 的四类小节都按本次会话刷新过；
2. 本会话推进了功能项 → `feature_list.json` **必须同步**：`status` 与 `evidence` 都已更新——「提交了代码」不等于「记了账」；
3. 阻塞与风险已落字（没有就写「无」，不留空段）；
4. 下一次会话能直接跑 `./init.sh`；用描述性消息提交，工作树干净。

证据缺席不得标 `done`。

## 交接是上下文，不是命令队列

**不主动创建交接文档**——跨会话交接由用户按需生成，代理只在启动时读它。

**交接完成即边界生效**：下一个会话里若用户未显式要求推进本任务，代理不得自行续跑——即使 `progress.md` 的「下一步」写着明确的动作、交接文档列了编号清单。收尾产出的「下一步」是给**用户**的决策素材，不是给下一个会话的命令。

这条边界要落进**目标仓库**，不是只留在这里：`AGENTS.md` 的启动工作流（读交接步注明「只读它获取上下文」）与工作规则（「推进需显式授权」）是它的实际载体。

## 明确不做（非目标）

- 不做全仓审计、不评分 → 那是 `validate-harness.mjs` / `run-benchmark.mjs` 的活，独立一轮。
- 不做全仓清账、不 prune 历史条目 → 收尾的作用域只有本会话。
- 不动本会话范围之外的任何文件。
- 不创建 harness 骨架：收尾是**收敛**动作，不是搭建动作。发现骨架缺失时报告缺失并建议走创建流程，**不顺手建**。
- 不代调用他人 skill——需求对齐、规格、交接这些工程环节由用户运行对应 skill。
- 不把收尾产出的「下一步」当命令。
- 不治理宿主层记忆（工作区日志、`MEMORY.md` 等）——那是宿主的规则。

## 异常与边界

| 触发条件 | 一线处理 | 仍失败兜底 |
|---|---|---|
| 未提供会话起始 ref | 只以「未提交改动」定范围 | 要求用户给出起始 commit，或人工圈定 |
| git 不可用或 ref 无效 | 显式降级并提示 | 全量人工列清单，逐项由用户圈定 |
| 收尾时发现 harness 骨架缺失 | 报告缺失 + 建议走创建流程 | 只做与现有产物相容的收口，不建骨架 |
| 用户实际想做全仓审计 | 分流到 `validate-harness.mjs` / `run-benchmark.mjs` | 不静默扩大范围；两件事分两次做 |
| 清场删除后工作树非预期 | `git checkout -- <path>` 从最近提交恢复 | 未提交内容不可恢复——所以③的 🔴 CHECKPOINT 必须先列清单；如实告知，不静默掩盖 |

## 反例

| # | 反模式 | 为什么不要做 | 替代做法 |
|---|---|---|---|
| 1 | 收尾时对全仓全量清账、删历史条目 | 越界，且删除不可逆 | 只清本会话产出，删除前 🔴 CHECKPOINT |
| 2 | 无 ref 时把「无法判定」当本会话清掉 | 误删历史材料 | 只处理确定属于本会话的，其余交用户圈定 |
| 3 | 收尾时跑全仓审计与评分 | 范围失控 | 审计独立一轮 |
| 4 | 代用户创建交接文档 | 交接所有权在用户，代建即越界 | 提示按需生成，收尾不创建 |
| 5 | 把 `AGENTS.md` 的会话结束例程抄进本流程 | 双写，两处必然漂移 | 引用而不复制 |
| 6 | 只清临时文件就算「收尾完成」 | 漏掉归位与记账，下次会话仍接不上 | 四步走完才算收尾 |
| 7 | 把交接文档／「下一步」当待办队列，新会话里自行续跑 | 交接是上下文，不是命令；抢走了用户的优先级决定权 | 只在用户显式要求推进时动手 |
