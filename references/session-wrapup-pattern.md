# 会话收尾（Session wrap-up）

**一句话**：把**本次会话的产出**收敛回五个落点，让下一次会话能立刻重新启动。

作用域是**会话**，不是仓库——这是它与「整理仓库」「优化」的唯一分界，也是唯一容易搞错的地方。

## 触发

用户调用本技能**且**表达收尾意图时触发。常见说法：「收尾」「会话收尾」「结束这次会话」「wrap up」「这次先到这儿」。

- 两个信号同时出现即触发，用户不必说出 "harness" 这个词。
- 只有收尾意图、没有显式调用本技能，但上下文正是本技能管辖的 harness 时，同样触发。
- 触发后**先分流**（见下节），不要直接开始删文件。

## 三个意图的分流（先判作用域，再动手）

| 用户意图 | 典型说法 | 作用域 | 动作 | 机器载体 |
|---|---|---|---|---|
| **会话收尾** | 收尾、结束这次会话 | **本会话产出**（起始 ref 之后的改动与新增） | 定界 → 归位 → 清场 → 记账 → 收口 | `scan-housekeeping.mjs --session-only` |
| **整理仓库** | 整理仓库、清账 | **全仓状态落点**（含历史累积） | 清账 / 查漏 / 补齐 | `scan-housekeeping.mjs` |
| **优化 / 审计** | 优化 harness、评估一下 | **全仓 harness 质量** | 五子系统审计 + 改进落地 | `validate-harness.mjs`、`run-benchmark.mjs` |

判据只有一条：**作用域**。本会话 → 收尾；全仓 → 整理；全仓质量 → 优化。

三者**不叠加**。收尾不 prune 历史条目、不跑全仓审计；用户若同时提出两种意图（"收尾，顺便优化一下"），拆开执行并说明作用域差别，不把优化塞进收尾。

## 作用域如何确定

**先定界，再动手。** 范围没定下来之前不改任何文件。

- 首选：会话起始 commit → `--session-ref`。范围 = `git diff --name-only <ref>` ∪ 未跟踪文件。
- 未提供 ref：**不假设 `HEAD`**（HEAD 会把已提交的本会话内容误判为历史）。此时只有「未提交改动」可确定为本次会话，其余标「无法判定」，**不得把「无法判定」当作「本会话」处理**。
- git 不可用：降级为人工列清单，由用户圈定本会话产出。
- 非 git 产出（只在对话里生成、从未落盘的内容）：收尾时判断它该不该落盘到落点；不落盘即视为丢弃，一句话说明即可，**不为它专门建文件**。

## 五步流程

### ① 定界（scope）

```bash
node <技能目录>/scripts/scan-housekeeping.mjs --target . --session-ref <会话起始 commit> --session-only
```

只读扫描，输出三类信息：本会话产出按落点的归类、`.scratch/` 中属本次会话、待裁决的材料、以及落在五落点之外的会话产出（候选未归位材料）。

### ② 归位（route）

逐个判断本会话产出该落在哪里。流转规则与仓库级治理同一张表，区别只是**只看本会话新增与改动的**：

| 本会话产出的东西 | 落点 |
|---|---|
| 决策与理由 | ADR（`docs/adr/`） |
| 代码表达不了的领域用语 | `CONTEXT.md` |
| 可执行约束（测试、Schema、门禁） | `init.sh` / CI |
| 跨会话有效的**长期不变量**（既非决策、亦非术语、亦非门禁） | 目标仓库 `AGENTS.md` 的「工作规则」节——受该节自身条目上限约束：先合并同族项，合并后仍超，就重新判断它能否落进 `init.sh`/CI |
| 状态与依赖 | `feature_list.json` / `progress.md` / 工单 |
| 需求 / spec | 未发布：任务级草稿进 `.scratch/`；已发布：并入工单（落点五），草稿不再保留 |
| 仍需使用的任务级草稿 | `.scratch/`（由收尾与整理按作用域分别清，不依赖任何自动机制） |
| 已无价值的任务级草稿 | 清场（③） |
| 业务代码 | 无需「归位」——代码即文档，随提交走 |

归位 = 写进落点，**引用而不复制**；同一事实只落一处（反例 #1）。

扫描器报出的「落点外会话产出」只是**候选**：文档类文件（`*.md` 等）优先复核——若它属于**项目文档层**（判据：代码表达不了 + owner 已在目标仓 `AGENTS.md` 的项目文档路由处按固定写法登记，格式以 `templates/agents.md` 的启动工作流第 5 步为准；缺 owner 与指向不存在路径的条目由扫描器体检点名），它本就不占五落点，收尾只当候选、不搬不移；否则按知识材料误留处理（归位或清场）。判不出来就问，不擅自搬移。

### ③ 清场（只清本会话）

清掉本会话新增且已无价值的临时材料：`.scratch/` 中属于本次会话的中间稿、为本次会话生成的一次性文件。

🔴 **CHECKPOINT**：删除前逐条列出「将删 / 将留」并获批准。

**本步不碰**：非本会话文件；历史累积的 `status=done` 且有 `evidence` 的条目（那是整理的活）；`status=done` 但缺 `evidence` 的条目（先补证据，不是抹痕迹）；指令文件（`AGENTS.md`/`CLAUDE.md`）的任何内容——包括豁免清单里的失效登记行，那同样是整理的活。

### ④ 记账（state）

**输入**：本会话推进的功能项；**输出**：状态文件里下一次会话可直接读到的证据。

按目标仓库 `AGENTS.md` 的「会话结束」一节执行——**引用而不复制**，本流程不重抄那几条。该节缺失时的最小动作：更新 `progress.md`（当前状态、证据、阻塞、下一步）→ 更新 `feature_list.json` 的 `status` 与 `evidence` → 记未解决的风险 → 干净提交。

**本步完成判据（缺一即未完成，逐项核对）**：

1. `progress.md` 的四类小节都按本次会话刷新过；
2. 本会话推进了功能项 → `feature_list.json` **必须同步**：`status` 与 `evidence` 都已更新，`done` 必有证据——「提交了代码」不等于「记了账」；
3. 阻塞与风险已落字（没有就写「无」，不留空段）。

- tracker 模式：状态在工单系统，仓内无状态文件即跳过本步，**不新建** `feature_list.json`；上述判据改为「工单状态与证据链接已更新」。
- 证据缺席不得标 `done`（反例 #3 的头号失败）。

### ⑤ 收口（close）

保证下一次会话能直接跑 `./init.sh`；用描述性消息提交，工作树干净。

**不主动创建交接文档**——跨会话交接由用户按需生成（matt handoff 或等价技能），落在 `.scratch/`，代理只在启动时读它。

**交接完成即边界生效**：交接文档是**上下文**，不是**待办队列**。下一个会话里若用户未显式要求推进本任务，代理不得自行续跑——即使 `progress.md` 的「下一步」写着明确的动作、交接文档列了编号清单。收尾产出的「下一步」是给**用户**的决策素材，不是给下一个会话的命令。

这条边界要落进**目标仓库**，不是只留在这里：`AGENTS.md` 的启动工作流（读交接步注明「只读它获取上下文」）与工作规则（「推进需显式授权」）是它的实际载体。本流程负责在收尾时声明它，并在收口时确认那一节存在。

## 明确不做（非目标）

- 不做全仓审计、不评分 → 那是**优化**。
- 不做全仓清账、不 prune 历史条目 → 那是**整理**。
- 不动本会话范围之外的任何文件。
- 不清 ADR（只增不删）与 `CONTEXT.md`（持续更新）——与整理共享的硬边界。
- 不创建 harness 骨架：收尾是**收敛**动作，不是搭建动作。发现骨架缺失时报告缺失并建议走创建流程，**不顺手建**。
- 不代调用他人 skill（沉淀类由用户运行）。
- 不把收尾产出的「下一步」当命令：交接完成后，新会话中用户若谈别的事，不推进原任务——推进需显式授权。
- 不治理宿主层记忆（工作区日志、`MEMORY.md` 等）——那是宿主的规则，不进本流程。

## 异常与边界

| 触发条件 | 一线处理 | 仍失败兜底 |
|---|---|---|
| 未提供 `--session-ref` | 只以「未提交改动」定范围 | 要求用户给出会话起始 commit，或人工圈定 |
| git 不可用或 ref 无效 | 扫描器显式降级并提示 | 全量人工列清单，逐项由用户圈定 |
| 会话产出落在五落点之外 | 报告为「待裁决」候选 | 用户裁决：归位，或明示「保留，不进落点」 |
| 收尾时发现 harness 骨架缺失 | 报告缺失 + 建议走创建流程 | 只做与现有落点相容的收口，不建骨架 |
| 用户实际想整理全仓 | 分流到整理，说明作用域差别 | 不静默扩大范围；两件事分两次做 |
| 用户想「顺手优化一下」 | 收尾先完成，优化另起一轮（validate / benchmark） | 不把审计结果混进收尾报告 |
| 清场删除后工作树非预期 | `git checkout -- <path>` 从最近提交恢复 | 未提交内容不可恢复——所以③的 🔴 CHECKPOINT 必须先列清单；确认丢失后如实告知，不静默掩盖 |

## 反例

| # | 反模式 | 为什么不要做 | 替代做法 |
|---|---|---|---|
| 1 | 收尾时对全仓全量清账、删历史条目 | 越界到整理的作用域，且删除不可逆 | 只清本会话产出，删除前 🔴 CHECKPOINT |
| 2 | 无 ref 时把「无法判定」当本会话清掉 | 误删历史材料 | 只处理确定属于本会话的，其余交用户圈定 |
| 3 | 收尾时跑全仓审计与评分 | 混淆「收尾」与「优化」，范围失控 | 审计走 `validate-harness.mjs`，独立一轮 |
| 4 | 代用户创建交接文档 | 交接所有权在用户，代理代建即越界 | 提示按需生成，收尾不创建 |
| 5 | 把 `AGENTS.md` 的会话结束例程抄进本流程 | 双写，两处必然漂移 | 引用而不复制 |
| 6 | 收尾时顺手创建缺失的 harness 骨架 | 收敛动作变搭建动作，范围再次失控 | 报告缺失 + 建议创建流程 |
| 7 | 只清 `.scratch/` 就算"收尾完成" | 漏掉归位与记账，下次会话仍接不上 | 五步走完才算收尾 |
| 8 | 把交接文档/「下一步」当作待办队列，新会话里自行续跑 | 交接是上下文，不是命令；用户没要求即越界，且抢走了用户的优先级决定权 | 只在用户显式要求推进时动手；边界写进目标仓库 `AGENTS.md` |

## 与既有规则的关系

- 与 `housekeeping-pattern.md` 共享三分法作用域与「ADR / `CONTEXT.md` 永不清」的硬边界，差别**只在作用域**。
- 与 `AGENTS.md` 模板的「会话结束」一节目的相同、触发不同：那一节是**每次会话结束都执行**的常驻例程；本流程是**用户显式发起的收尾**，增量在②归位与③清场。
- 交接所有权不变：handoff 由用户按需生成，收尾只清理过期的，不创建新的。
