# 技能运行时模式

当你想把可复用的代理行为打包为技能，而不是在每个仓库中重复冗长的指令时，使用本模式。

## 什么应该放进技能

- 跨项目适用的可复用工作流。
- 特定领域的决策程序。
- 代理应按需加载的模板、清单与参考材料。
- 稳定且可安全运行的小型辅助脚本。

## 什么不应该放进技能

- 应放在目标仓库中的项目特定架构事实。
- 机密、令牌、私有 URL 或用户专属凭据。
- 代理在行动前必须通读的大型手册。
- 具有破坏性副作用的命令，除非已明确记录并要求用户显式批准。

## 运行时形态

生产级技能应采用渐进式披露：（来源：pstack guide，https://github.com/cursor/plugins/blob/main/pstack/docs/guide/README.md）

1. `SKILL.md` 的 frontmatter 说明技能应在何时触发。
2. 正文给出最短的可靠工作流。
3. `references/` 存放仅在相关时才加载的深入材料。
4. `templates/` 存放可复制的产物。
5. `evals/` 记录代表性的质量检查。

## 设计规则

- 入口文件保持简洁，可快速浏览。
- 优先使用具体清单，而非抽象建议。
- 链接每个被引用的随附文件并验证其存在。
- 安装说明须明确仓库、技能名称与目标代理。
- 将脚本视为可选的辅助工具，而非隐藏行为。

## eval 与基准怎么设计

结论先行：这是两件不同的事，一个分数不能同时代表它们。**结构性自检**是脚手架加机械断言，回答「脚本跑得起来吗、断言本身对不对」，它必须能 `exit 0`。**代理行为 eval** 是给代理一批目标任务，回答「代理在该做什么时实际做了什么」，它不能被脚本执行。`SKILL.md` 列的三种非零退出来源里，自检 FAIL 与 harness 得分是脚本判的，eval 覆盖那一项评的是 eval 文件自身的结构，不代表任何一次代理行为。

### eval 条目的最小字段

- `prompt`：一次真实会话里会出现的任务，带上约束条件（新项目、已有 harness、用户纠错），不是功能清单。
- `expected_output`：产物形态与边界，写「哪几个文件、多不多不少」，不写「质量高」。
- `expectations`：至少三条可观察判据。

判据必须是可判定的事实。「只创建 AGENTS.md 与 init.sh，不新增目录层」可判定，「回答清晰」不可判定。形容词一旦不可判定，评估就退回「看起来对」，而「看起来对」恰好是代理最容易投其所好的地方。（来源：pstack guide，https://github.com/cursor/plugins/blob/main/pstack/docs/guide/README.md）

本仓 `evals/evals.json` 的 22 例就是这个形态，每例含 prompt / expected_output / expectations，`files` 字段一律为空数组：刻意不指定要读哪些文件，避免 eval 退化成存在性检查。

### 什么算无效的 eval

- 只检查存在性：文件在不在、目录建没建。它证明脚手架完整，不证明代理行为。
- 只检查关键词与措辞：这就是 `SKILL.md` 反例 #5 说的「为通过 validate 审计堆砌关键词」。词能被检索到，改动未必发生。
- 样本不足以区分两种设计：所有判据在换一套明显不同的实现后仍然全过，等于没测。至少要有一到两条只在新实现下才会过的判据。
- 判据与实现耦合：把当前实现的写法抄进判据，等于把实现固化成契约，改对了反而判失败。

### 前后对照怎么做才算数

四个条件缺一不可：同一基座与模型版本、同一任务集、一次只改一个变量、记录反例样本（做错的具体输出，不是错了几次）。

没有对照就只能说「结构更完整」，不能说「代理更可靠」。这是 README 里「无前后对照，不宣称代理效果提高」那条约束的适用范围。

### 分不达标时先看哪一层

eval 覆盖低于阈值时按顺序排查，先确定是哪一类再动手：

1. 目标集太弱：某个能力族没有条目，或条目名已不再代表该族。动作是补一条能区分新旧实现的 case，并登记进覆盖契约（本仓用 `familyEntries` 与孤儿守卫两个方向卡）。
2. 判据不可判定：expectations 里混着形容词或不可观察的说法。动作是把每条改写成「X 存在 / 不存在 / 恰好 N 个」。
3. 样本不足：条目数不够，或一条 entry 匹配多条 case。动作是拆开或补样本，不放宽阈值。
4. 实现回归：结构分掉了但 eval 文件本身没变。动作是回去查实现，不是改 eval。

前三类都能在 eval 文件内修完；第四类必须回到实现，调 eval 掩盖它是自欺。

### 证据等级

`evals/evals.json` 给出的覆盖分是**结构性证据**：它只证明 eval 文件覆盖了各能力族、字段齐全、没有孤儿条目。它不由模型执行，也从不判定代理行为。

`test-prompts.json` 是**人工会话实测材料**，不被任何代码执行，因此既不能进自动化门禁，也不构成通过率。

两者都不等于「代理做对了」。真实效果只能另跑代理会话并核对产物。
