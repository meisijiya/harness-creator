# 旁路观测模式：断言真实决定的检查，不是复述实现的检查

本文件只出设计，**不接管任何写入**。要不要建这个入口、建在哪、第一条检查写什么，都是项目自己的
决定；本文件不生成、不改写、不注册它。

## 为什么要有「旁路」

绝大多数项目里的测试，是写代码那一轮的副产品：功能刚落地，顺手写下"验证它能跑"的东西，断言跟着
实现走。于是门禁只证明了「实现和它的测试出自同一段推理」——而这正是需要被独立观察的那件事。

旁路观测要的不是"换个人来写"。它要的是：这条检查断言的，是**事先真的做过决定的那个期望**，而不是
实现者给自己开的绿灯。

### 协作形态：harness 是作用于 AI 的

先说清一件事，否则判据会定错：harness 服务的是 AI，人与 AI **一同维护**它——AI 承担大部分工作，
**决策交给人**。因此：

- 入口脚本大概率由 AI 写，也大概率由 AI 改；
- 它的设计来自人与 AI 的讨论，不存在"纯人工写"的那一部分；
- 真正属于人的只有一样：**决定**。

所以"作者是人还是 AI"这条判据是错的。按它执行，这条旁路在真实协作方式下永远建不起来，而它本来
是成立的——**没有任何一条旁路能靠"这次我亲手敲了"来达标。**

### 「独立于模型」的可判定判据

判据只有一条，而且必须可判定：

> **这条检查断言的期望，能不能指到一次真实的决定上。**

指得到 = 独立。指不到 = 自证。**不论代码是谁敲的。**

可判定的操作版本：

- 有人说过要对错——需求、约定的不变量、"这种情况绝不能发生"——检查正是把它断言下来 → **独立**。
  哪怕整份文件、每一行都是 AI 写的。
- 检查的唯一依据是"实现现在就是这么做的" → **自证**。哪怕写的人反复声明自己很认真。

差别不在谁写的，在**期望有没有出处**。AI 写的代码背后常常确实有一个真决定（那正是它写得出这段代码
的原因）；而"顺手补个测试让它变绿"背后没有——那种门禁是在**追认实现**，不是在检验决定。

> **不要用"覆盖是否关键路径"来代替这条判据。** 那是质量判断，而且关键模块上照样可以写一条纯自证的
> 测试。要问的是"这个期望从哪来"，不是"这个模块重不重要"。

## 从哪开始：高位模块优先

第一个入口不要从"最容易写的地方"开始，从**改坏了代价最大的地方**开始。

排序依据是**失败不可逆性**，不是覆盖率、不是代码量、也不是实现难度：

| 优先 | 模块 | 为什么 |
|---|---|---|
| 1 | 登录、会话、权限判定 | 放行一个不该放行的人，比拒绝一个合法用户更难被发现，且常常到出事才被发现 |
| 2 | 支付、计费、配额 | 金额与配额的错误不会自己暴露，往往在下一个对账周期才显形 |
| 3 | 数据写入与迁移 | 不可回滚；破坏通常静默 |
| 4 | 对外契约（接口响应结构、状态机） | 会让下游一起坏，但通常会立刻暴露 |
| 5 | 业务规则 | 最容易写，也最晚被做错——放最后，不是因为不重要，是因为它可逆、可观察 |

**不要**从"已经有一半测试的地方"开始。那是舒适区，不是风险区：那里本来就是这套项目里最先有人
关心的地方。

## 只增不修

旁路入口里的检查，红了转绿之后就**冻结**：以后只往上加，不改、不删、不放宽。

这条和"门禁只增不修"同源，但在这里更硬：

- 一条已经转绿的检查是**既成事实的证据**。删掉它、或者把断言从 12 条减到 3 条让它好过，等于把
  一份已经拿到的证据退回去，而没有人会注意到证据变少了。
- 改一条已经绿的检查，必须在同一次改动里说明**为什么当初那条是错的**。说不出理由的修改，
  多半不是修正，是让门禁变绿的手段。
- 断言放宽（`assertEqual` → `assertNotNone`、删掉一个 case、把精确匹配改成模糊匹配）**比新增检查
  更危险**：它让门禁从"检查这件事"退化成"检查过这件事"。

判断标准很直接：**改完之后，这条检查还能在同样的输入上抓住当初那个 bug 吗？** 说不出具体 bug 的
改动，是别的目的。

## 反向验证：亲手制造一次失败

一条从没红过的门禁，和一个不存在的门禁，在输出上没有区别。它可能是因为实现一直对而一直绿，也
可能是因为它压根没被执行、路径写错了、或者断言写得太松——**这三种情况都输出"通过"**。

所以：**每加一条检查，必须亲手制造一次它会失败的输入，把原始输出贴出来。**

要求写清楚，是为了让这件事无法被含糊过去：

1. **贴原始输出**，不是"我试了，它红了"。要包含退出码，以及门禁自己打印的失败行。
2. **包含非零退出码**。只看输出里的 "FAIL" 字样是不够的——那可能来自某个被忽略的中间步骤。
3. **做完必须还原**。故意失败的那次改动不许留在仓库里；还原后再跑一次门禁，确认它绿，且这一次的
   绿才是可信的基线。
4. **门禁红了才算数**。如果制造失败之后门禁依然绿，那就是检查没生效——按上面三种可能逐一排查，
   不要记成"已验证"。

第 3 条有具体的坑：`git checkout -- <文件>` 恢复的是 **HEAD**，不是"探针之前"。如果同一文件里
还有本次工作之外的未暂存改动，它们会一起消失，而且 `git status` 会变干净——**丢失表现为整洁**。
正确做法是把原文先留在内存里或临时副本里，再写回去。

## 挂到门禁上的方式

入口脚本放在目标仓自己手里，`init.sh` 里只加**一行**无守卫的调用：

```bash
# 由 create-harness.mjs --add-check-entry 追加，或手写，效果相同
./verify.sh
RAN=1
```

**不要加 `[ -x ./verify.sh ]` 之类的守卫。** 守卫的效果是：入口被删了 → 跳过 → 门禁照样打印
"完成"并退出 0。一个会跳过自己的门禁比没有门禁更糟，因为它把退化报告成了通过。

入口不存在、被删、不可执行时，让门禁**红**（`set -e` 下的未守卫调用会自然做到：缺文件退 127，无执行
权限退 126），这是正确状态，不要用守卫把它变成绿灯。

## 什么时候这一套不适用

- **一次性脚本、文档仓、教学材料**：没有需要长期观察的行为，写了也没人会跑。
- **检查只能复述实现**：断言背后的"期望"指不到任何一次真实决定——那它是自检，不要记成独立验证。
  这条与文件由谁写无关：整份 AI 写的入口脚本里，一条断言真实决定的检查仍然成立。
- **已经有人的测试套件在跑**：不要再建第二个入口。把这条"独立于模型"的要求落到已有的那一套上，
  比多一个入口便宜得多。

## 一条工作规则怎么变成一条检查

结论先行：一条工作规则只有同时满足下面几条，才值得搬进门禁；缺任意一条，它就该留在 `AGENTS.md`
里继续当文字规则。搬进去分两步：先按判据决定**要不要搬**，再按落点规则决定**搬到哪里**。本节只管这两步，
不管搬进去之后断言什么。

### 能门禁化的判据

逐条可判，每个代理都能照着执行：

1. **可重复**：无人介入的情况下跑两次，结论一致。判法是把规则里"看一眼再决定"或"凭经验觉得"的地方
   揪出来（"目录不要太乱"、"命名要一致"），揪到就是否。
2. **失败非零**：违反时有一条命令以非零码退出。判法是故意违反一次读退出码，只看输出里的 `FAIL`
   字样不算数，那可能来自一个被忽略的中间步骤。
3. **失败可归因**：退出时能指出是哪个产物、哪条规则不满足，而不是笼统失败。判法是看门禁打印的
   那一行够不够让人不必翻日志就知道该改哪个文件。
4. **只读**：检查过程不改任何被检查的产物。判法是跑一次之后 `git status` 必须干净；检查顺手改
   文件，就不再是检查，是生成。
5. **输入来自工作区**：判据数据取自仓库内文件，不取自网络、不取自人脑。判法是断网再跑一次，结论不变。

### 不该门禁化的判据

这几类一律留在 `AGENTS.md` 的工作规则里，写成"什么时候该做什么"，而不是"什么时候算失败"：

- **需要人判断的量**：设计取舍、范围是否合理、抽象是否过度。门禁能给它们打分，但打分不改变判断
  本身，只会在分数漂移时逼人放宽阈值。
- **需要外部凭据的量**：token、私有依赖、公司内网服务。门禁在别人机器上跑，缺凭据就变成假红，
  而假红每次都要有人手动绕过去。
- **有副作用的量**：跑起来要装包、要发布、要改数据库、要发请求。有副作用的检查在别人机器上第一次
  触发时，破坏面比它抓到的 bug 大。
- **随时间漂移的量**：版本号、依赖树、文件行数、评分阈值。这类量今天过明天不过，进门禁之后每次都要
  放宽阈值，很快回到"绿灯即通过"。

### 落点选择：内联一步，还是无守卫的一行

- **内联一步进 `init.sh`**：检查只有一条命令、只依赖仓库内文件、别处不会再引用它。做法是
  `--add-check`，只追加，不动旧步骤。
- **写进项目自己的脚本，门禁里只留一行调用**：检查要复用、超过一条命令，或者项目已经有一个跑检查
  的脚本（测试套件、lint 配置）。做法是 `--add-check-entry`。那一行的关键性质是**入口没了要让门禁
  变红**，所以**不要写 `[ -x ./verify.sh ]` 之类的守卫**：缺文件退 127，无执行权限退 126，`set -e`
  下的未守卫调用自然把门禁拉红。加了守卫，入口被删就变成跳过，门禁照样打印"完成"并退出 0，把退化
  报告成了通过。

### 从踩坑到检查

一条门禁红过的原因要变成新检查，必须写成**发现方式**，只贴命令不算数。四问：

1. 这次是怎么发现的：报错文本、人工发现，还是下一次事故。答不上来说明它还没被真正观测到，先补
   观测，别急着写检查。
2. 当时的**期望**是什么，也就是背后那次真实决定，而不是当时的行为长什么样。
3. 违反一次，看门禁是否真的红（按上面第 2 条判），把原始输出和退出码贴出来。
4. 还原改动，确认这一次绿才是可信的基线。

### 三条假检查

- **把散文规则逐字抄进脚本**：拿 `grep` 去找 `AGENTS.md` 里那句规则的原文，找不到就非零退出。规则
  文本只要还在仓库里就永远绿，改一个字又立刻红。它断言的是"文档长这样"，不是"约束被满足"，必然
  恒过。判法：改掉规则原文里一个不影响含义的词，看这条检查是否变红，会红就说明它只在盯文本。
- **把散文规则写成注释或 `echo`，紧跟一条真检查**：检查真做了，但那句散文是摆设，人会以为它被断言
  了，规则与检查之间的漂移就再没人发现。要求脚本里每一条非零退出都能对上一条可命名的规则。
- **失败被吞掉**：`! grep -q ... && echo ok` 这类写法，`grep` 未命中退出 1，被 `!` 取反后翻成
  "通过"，在 `set -e` 下也不中断。判法同上：故意违反一次，看不到非零码就是失败被吞了。

## 与本技能其他部分的边界

本技能负责的是**指令文件**与**验证入口**这两件产物的形态：门禁长什么样、检查怎么被追加、哪些东西
不许写进产物。检查**内容**——断言什么、覆盖哪些模块、什么算通过——是项目的决定，本技能不生成、
不评价、不推断。
