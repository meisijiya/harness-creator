# 非工单模式的任务推进（补齐 `implement` 的缺位）

**一句话**：tracker 模式的推进由 matt 的 `implement` 承接；registry 模式没有工单系统，所以 `feature_list.json` 的每个条目**就是**一张工单，推进它必须复用同一套纪律——曳光弹式垂直切片、blocking edges、一次一个、先验证再声称完成。

**前提**：默认用户已在本机装好两套上游工程 skill（`mattpocock/skills`、`addyosmani/agent-skills`）。本文档不复制它们的正文，也不维护 skill 名单——**清单与调用模式见 [Upstream Interlock](./upstream-interlock.md)**；本文档只写 registry 侧缺口的补齐。

作用域是**推进**（把一条 feature 做完），与**收敛**（收尾、整理）正交，见文末「与既有规则的关系」。

## 为什么需要本文档

- tracker 模式（matt 工程流）里，纪律由外部 skill 承接：拆分与执行各有对应的上游 skill（名单与调用模式见 [Upstream Interlock](./upstream-interlock.md)）。**这条链已经齐了，本文档不重复它。**
- registry 模式没有这层结构：没有工单系统、没有 `implement` 可挂钩的对象，纪律全靠 harness 自身承接。缺了补齐，registry 的「下一步」会退化成「按注册表顺序写代码」——横向切片、无验收标准、无证据。
- 两个模式的区别只在**状态存放位置**，不在工程纪律。所以本文档只做一件事：把 tracker 侧已有的那套规范，平移到 `feature_list.json` 上。

## 两个模式的等价映射

| tracker 模式（已由上游承接） | 上游 skill | registry 模式的等价物 | 落点 |
|---|---|---|---|
| 拆分：曳光弹垂直切片 + blocking edges | 上游的拆分 skill（用户调用） | 拆 `feature_list.json` 条目：`description`（交付什么）+ `dependencies`（被谁阻塞）+ `acceptance`（验收标准） | `feature_list.json` |
| 推进：按 spec/tickets 实现 → 预定接缝跑测试 → 定期类型检查与单测 → 末次全量 → 审查 → 提交 | 上游的执行 skill（用户调用） | 同一节奏，触发条件是「用户显式要求推进某 `feat-XXX`」 | 会话内 |
| 测试纪律：先红后绿、接缝预先商定、垂直切片 | 上游的测试 skill（模型可调用） | **同一能力，直接复用** | 测试代码 |
| 拆分纪律：有序任务、执行依赖、并行可能 | 上游的任务拆解 skill（模型可调用） | **同一能力，直接复用** | 会话内 |
| 增量环：实现 → 测试 → 验证 → 提交，范围纪律、保持可编译、回滚友好 | 上游的增量实现 skill（模型可调用） | **同一能力，直接复用** | 提交序列 |
| 审查 | 上游的审查 skill（模型可调用） | **同一能力，直接复用** | diff |
| 验证门禁 | CI | `init.sh` + `acceptance` 逐条勾选 | `init.sh` / CI |
| 证据 | 工单上的 CI 链接 | `evidence` 字段（命令 + 结果摘要） | `feature_list.json` |
| 交接 | 上游的交接 skill（用户调用） | 同 | `.scratch/` |

**引用而不复制**：上表只记**环节与角色**，具体 skill 名、仓库归属与实测调用模式见 [Upstream Interlock](./upstream-interlock.md)——**清单只在那一处维护**。上游改名、合并或增删 skill 时，本表无需跟着改；把上游正文搬进本仓库则等于维护一份必然腐化的副本（反例 #8）。

## 与上游的联动方式

上游 skill 分「模型可调用」与「用户调用」两类，处置不同：

- **模型可调用**：推进时**可直接调用**，无需用户先开口——它们是 registry 模式推进的默认动作集。
- **用户调用**：**由用户发起**，代理不代发起。其中「执行」那一环挂在工单上，registry 模式没有它可挂的对象——**这就是本文档要补的缺口**：`feature_list.json` 条目扮演它的输入，推进节奏按下面两节的规范由代理自己承接。

「承接」不等于「复刻」：不新建一份执行 skill 的仓内副本，只把它的节奏落成条目字段与推进步骤。**角色到具体 skill 的映射、插拔规则与上游变更维护流程，见 [Upstream Interlock](./upstream-interlock.md)。**

## 拆分规范（内化自上游的曳光弹纪律）

- 每条 feature 是一条**垂直切片**：穿过所有层（数据、接口、界面、测试）的窄而**完整**的路径，不是一个层的横向切片。
- 切片完成后**可独立演示或验证**；无法独立验证，说明切错了。
- 切片**尺寸以单个新上下文窗口为限**（上游拆分与任务拆解 skill 的硬规则，也是判「任务太大」的标尺）。
- `dependencies` 就是 blocking edges：只声明真正阻塞它的条目。无阻塞的条目可立即开工，即「前沿（frontier）」。
- 先做 prefactor——**先把改动变容易，再做容易的改动**：记为独立条目，排在依赖它的条目之前。
- **宽重构是例外**：一次机械改动（重命名列、改共享符号的类型）影响面横扫全仓时，不要硬塞进垂直切片，改用 **expand–contract**——先并列新增（旧形式仍在）、再分批迁移调用点（每批一个条目、被 expand 阻塞）、最后在无调用方时删除旧形式。
- 条目里**不写具体文件路径或代码片段**（很快过期）。例外：原型产出的、比散文更能精确表达决策的片段（状态机、reducer、schema、类型形状）可内联，并注明来自原型。

## 推进规范（内化自上游的执行与增量实现纪律）

一次会话推进**一条** feature，按固定节奏：

1. **选前沿**：只挑阻塞项全部完成的条目，一次一条。
2. **定接缝**：动手前写清要测的公共边界（seam）并与用户确认；**未经确认的接缝不写测试**。测试只落在接缝上，不针对内部结构。
3. **跑增量环**：实现最小完整片段 → 测试 → 验证 → 提交，循环往复；不攒大批改动。
4. **先红后绿**：先写失败的测试，再写刚好让它通过的代码；不为想象中的未来测试提前铺代码。
5. **范围纪律**：只碰本条 feature 需要的文件。发现边界外值得改的东西，**记下来、不动手**，交由用户决定是否新建条目。
6. **保持可编译**：每个增量之后项目都能构建、既有测试都通过，不留半破状态。
7. **回滚友好**：每个增量可独立回滚；不要把「删除旧的」与「新增替代」放在同一次提交。
8. **收口**：上游的审查 skill 或等价审查 → 全量验证 → 写 `evidence` → 提交。

节奏失常的信号：改动超过约 100 行仍未跑测试；一次增量里混入多件不相关的事；为「以后可能要用」提前建抽象；「顺手也改了吧」的范围膨胀。

## 完成的判据

条目算完成，必须**同时**满足：

- `acceptance` 逐条验证通过；
- `evidence` 非空——可复现的命令与结果摘要，或 CI 链接；
- 仓库仍能从 `./init.sh` 起跑。

「代码写完了」不等于完成（反例黑名单 #3）。缺 `acceptance` 的条目无法判断完成，所以**拆条目时就写验收标准**，不留到声称完成时补。

## 边界

- **推进需要显式授权**：任务收尾并完成交接之后，若用户在新会话里讨论的是别的事，**不得**自行推进原任务。交接文档、`progress.md` 的「下一步」、`feature_list.json` 的待办条目都只是**上下文**，不是待办队列。
- **按角色联动而不复制**：默认上游 skill 已安装；角色到具体 skill 的映射见 [Upstream Interlock](./upstream-interlock.md)，本文档不重复维护名单。缺失时提示用户安装，不落仓内替代品、也不改写上游规范。
- **不改变 tracker 模式**：拆分与推进由上游那条主链接着走，不动它。不要因为读到本文档，就在 tracker 仓库里建 `feature_list.json`——那是第二状态源（反例黑名单 #1）。

## 反例

| # | 反模式 | 为什么不要做 | 替代做法 |
|---|---|---|---|
| 1 | 按注册表顺序「从上往下写」，不判依赖 | 先决项未完成就动手，违背阻塞边纪律 | 只推进前沿上的条目 |
| 2 | 横向切片：先写完所有数据层，再写所有接口层 | 大批无法验证的改动堆在一起，出问题无从定位 | 垂直切片，每片可独立验证 |
| 3 | 条目缺 `acceptance`，靠「看起来做完了」收工 | 无验收标准，done 退化为主观判断 | 拆条目时同时写验收标准 |
| 4 | 把「跑过一次测试」当证据 | 证据必须可复现，否则下个会话只能重跑或相信 | `evidence` 写命令 + 结果摘要 |
| 5 | 同一次提交里既重构又加功能 | 评审与回滚同时变难 | 拆成独立条目与独立提交 |
| 6 | 顺手修复边界外的问题 | 范围失控的主要来源，且绕过用户对优先级的决定 | 记下来交给用户决定 |
| 7 | 交接后用户没提任务，就自动续跑原任务 | 交接是上下文，不是命令队列；用户没要求即越界 | 只在用户显式要求推进时动手 |
| 8 | 把上游 skill 的正文抄进本仓库 | 上游升级即漂移；等于维护一份会腐化的副本 | 只记环节与角色；名单归 [Upstream Interlock](./upstream-interlock.md)，不在本仓维护副本 |
| 9 | 把整条大 feature 一次做完再验证 | 违反「尺寸以单个上下文窗口为限」，中途失控且无反馈 | 拆到可独立验证的粒度再推进 |
| 10 | 因为没有上游的执行 skill 可挂，就跳过测试与审查直接提交 | registry 缺的是挂载点，不是纪律 | 用模型可调用的上游测试/审查 skill 补齐同一节奏 |

## 与既有规则的关系

- 与 `templates/agents.md` 工作规则的「一次一个功能」「依赖清晰」「必须验证」「保持在范围内」同源：那几行给出**不变量**，本文档给出**怎么切**与**怎么推进**。二者引用而不复制。
- 与 `session-wrapup-pattern.md`、`housekeeping-pattern.md` 的分工：那两者管**收敛**（归类、清场、记账），本文档管**推进**（把一条 feature 做完）。三者的作用域互不叠加。
- 与 `matt-coexistence.md` 的分工：那一篇管 tracker 模式的**分区所有权**（谁写哪个文件），本文档管 registry 模式的**推进纪律**（一条 feature 怎么走完）。
