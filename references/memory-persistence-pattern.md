# 记忆与持久化模式

## 问题

没有持久化记忆，代理在会话结束的瞬间就会丢失所有用户偏好、项目上下文与行为反馈。用户每次会话都要重复纠正（"用 bun，别用 npm"），代理也无法积累那些使其随时间推移真正有用的工作知识。

## 黄金法则

### 按作用域与持久性分层

- **指令记忆**（人工维护、纳入版本控制）：AGENTS.md、CLAUDE.md、项目约定
- **自动记忆**（代理写入、持久保存）：进度日志、会话交接、发现的模式
- **会话提取**（后台派生）：会话结束时自动分析对话记录

### 两步保存不变量

每次记忆写入都是两步操作：
1. 将完整内容写入专属的主题文件
2. 向索引追加一行指针

如果进程在两步之间崩溃，最坏结果只是留下一个孤立的主题文件——索引仍保持一致。

### 本地覆盖永远优先

当同一主题在多个作用域被提及时，最局部的指令优先：

```
组织级 → 用户级 → 项目级 → 本地覆盖
   ↓         ↓         ↓         ↓
 设定底线   收窄范围   进一步收窄  最终决定
```

### 索引是有界的常驻上下文；主题文件是按需加载的细节

- **索引**：硬性上限约 200 行 / 25KB，每条一行
- **主题文件**：细节不限，按需加载

## 何时使用

- 代理跨会话存续，必须回忆用户偏好或项目上下文
- 多个作用域的指令并存，需要明确的优先级排序
- 代理应能从会话中学习而无需人工整理
- 需要不阻塞用户的后台提取

## 权衡

| 决策 | 收益 | 代价 |
|---|---|---|
| 分层记忆 | 每个作用域可独立共享、审计、覆盖 | 启动时需要发现更多文件 |
| 本地优先 | 用户无需改动共享文件即可覆盖 | 全局规则可能被静默覆盖 |
| 有界索引 + 按需主题 | 无论记忆量多大，上下文成本恒定 | 代理必须多走一步检索 |
| 后台提取 | 不增加用户响应延迟 | 提取与下一轮对话之间存在竞态窗口 |

## 实现模式

1. 启动时幂等地**定义记忆目录**（如 `.claude/memory/`）
2. **创建索引文件**，在读取时强制执行硬上限
3. **实现两步保存**：先写主题文件，再更新索引
4. 仅在最终响应完成且无待处理工具调用后**触发后台提取**
5. **强制互斥**：如果主代理在该轮已写入记忆，则跳过当轮提取
6. **建立评审机制**，用于跨层提升的提议

## 陷阱

1. **索引截断在触发前是静默的** —— 条目保持简短
2. **优先级排序违反直觉** —— 本地 > 项目 > 用户 > 组织
3. **提取时机造成竞态窗口** —— 用户可能在提取完成前就开始下一轮
4. **可推导的内容不属于记忆** —— 架构与代码模式可从代码库重新推导
5. **孤立主题文件会累积** —— 建议定期清理

## 模板：进度日志结构

```markdown
# 会话进度日志

## 当前状态（最后更新：YYYY-MM-DD HH:MM）

**活动功能：** feat-003 - 带引用的问答
**状态：** 进行中（60% 完成）

### 已完成
- [x] 文档分块流水线
- [x] 索引数据结构
- [ ] 问答处理器（进行中）

### 进行中
- 正在实现问答 IPC 处理器
- 待定：流式响应还是批量响应

### 阻塞项
- 等待决策：引用格式（脚注还是行内）

### 下次会话应做
1. 完成问答处理器
2. 添加引用格式化
3. 端到端测试流程
```

## 证据

本模式基于生产级代理运行时（包括 Claude Code 的记忆系统），其实现包括：
- 四级指令层级（组织/用户/项目/本地）
- 四类自动记忆分类（用户/反馈/项目/参考）
- 带互斥的后台会话提取
- 作为扩展层的团队共享记忆
