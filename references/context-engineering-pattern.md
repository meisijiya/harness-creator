# 上下文工程模式

## 问题

上下文管理不善时，代理会失败：
- **上下文过多** → 会话启动缓慢，token 成本爆炸，模型淹没在细节中
- **上下文过少** → 代理做出错误假设，重复造轮子，违反约定
- **上下文错误** → 代理关注底层细节，遗漏架构约束

上下文不是大杂烩，而是必须用显式操作来管理的预算。

## 黄金法则

### 四种上下文操作

窗口中的每个 token 都应通过四种操作之一赢得自己的位置：

1. **SELECT（选择）** —— 即时加载上下文，而非一次性全量加载
2. **WRITE（写回）** —— 代理写回持久化存储（记忆、状态、规则）
3. **COMPRESS（压缩）** —— 会话中途对较早轮次做响应式压缩
4. **ISOLATE（隔离）** —— 委派的工作不得污染父上下文

### 渐进式披露

三层加载：

```
第 1 层：元数据（常驻，廉价）
  → 功能列表、记忆索引、会话状态

第 2 层：指令（激活时加载）
  → AGENTS.md、技能正文、风格指南

第 3 层：资源（按需加载）
  → 架构文档、API 参考、示例
```

### 记忆化昂贵的构建器，显式失效

上下文构建器（如"加载所有最近的 git 提交"）应做记忆化以避免重复工作，但**必须**在已知的变更点显式失效——而不是被动失效。每个变更点都必须清除对应的缓存。

## 何时使用

- 长会话中代理性能下降
- 因急切加载上下文导致启动缓慢
- 委派的工作污染父上下文
- token 成本不可预测

## 权衡

| 决策 | 收益 | 代价 |
|---|---|---|
| JIT 加载 | 启动快，空闲成本低 | 技能激活前代理无法对其推理 |
| 每块硬上限 | token 预算可预测 | 可能截断有用的上下文 |
| 手动缓存失效 | 无被动陈旧 | 开发者必须在每个变更点添加失效 |
| 委派隔离 | 父上下文干净 | 子代理看不到父代理积累的上下文 |

## 实现模式

### 选择模式（Select）

```markdown
## 启动上下文（立即加载）

- 仓库根路径
- 技术栈（一行）
- 来自 feature_list.json 的活动功能 ID

## 按需上下文（触发时加载）

- 技能：激活时读取
- 架构文档：实现新功能时读取
- API 参考：调用外部服务时读取
```

**关键动作：**
- 审计每轮当前的上下文成本
- 对每个变长块施加硬上限
- 添加截断恢复指引（"调用 list_files 获取完整输出"）

### 压缩模式（Compress）

长会话会耗尽窗口。响应式压缩：

1. **触发**：上下文用量超过阈值（如 80%）
2. **摘要**：较早的轮次（按 token 数的前 50%）
3. **保留**：最近的上下文（最后 20% 的轮次）
4. **标记**：将快照标记为"在第 N 轮压缩"

```markdown
## 会话摘要（第 1-15 轮，已压缩）

**目标**：实现带引用的问答功能
**已做决策**：
- 使用流式响应优化体验
- 引用格式：[doc:chunk] 行内引用
**创建的关键文件**：
- src/services/QaService.ts
- src/shared/types.ts（扩展了 QaResult）
```

### 隔离模式（Isolate）

委派的工作不得污染父上下文：

| 模式 | 上下文共享 | 最适合 |
|---|---|---|
| **协调者**（零继承） | 无 —— 工作者从零开始 | 复杂的多阶段任务 |
| **分叉**（全继承） | 完整 —— 仅限单层 | 快速并行拆分 |
| **蜂群**（点对点） | 共享任务列表 | 长时间运行的独立工作 |

**关键约束**：分叉仅限单层 —— 递归分叉会让上下文成本指数级膨胀。

## 陷阱

1. **大多数异步工作跳过"pending"状态** —— 工作单元直接注册为"running"
2. **上下文构建器被记忆化但需手动失效** —— 不加失效就会面对陈旧数据
3. **截断在触发前是静默的** —— 硬上限在读取时强制执行
4. **隔离边界必须在调用时强制执行** —— 不要只是把工具从提示词里移除

## 模板：上下文预算

```markdown
## 上下文预算（会话）

| 类别 | 预算 | 当前 | 状态 |
|----------|--------|---------|--------|
| 系统提示词 | 2,000 | 1,850 | ✓ |
| 指令文件 | 3,000 | 2,400 | ✓ |
| 记忆索引 | 1,000 | 600 | ✓ |
| 会话历史 | 10,000 | 4,200 | ✓ |
| 工作上下文 | 15,000 | 3,100 | ✓ |
| **合计** | **31,000** | **12,150** | 已用 39% |

**压缩触发点**：80%（24,800 token）
**下一步动作**：在 24,800 token 时触发压缩
```

## 证据

上下文工程模式见于生产级代理运行时，其中：
- 上下文预算是显式的，而非隐式的
- 渐进式披露将启动延迟降低 60-80%
- 手动缓存失效避免了微妙的陈旧性缺陷
- 隔离模式实现了可靠的多代理协调
