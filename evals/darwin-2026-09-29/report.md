# harness-creator 优化验收（2026-09-29）

结论：保留本轮修改。三个独立 paired judge 对同一基线与候选版本的裁决为 **3–0 better**：A clear、B slight、C clear。没有计算绝对总分，也没有推断生产成功率提升。

## 范围与依据

基线：`86eef1e7e6bed907fde3d1424d8b6a69325444e8`。分支：`auto-optimize/20260929-0122`。

用户指定的现版本样本为 agent-skills 的生成结果与 P1 的维护结果。重新读取后，P1 已是 98 行的较新版本；旧 110 行快照中已被修正的问题不再列为当前缺陷。本轮未修改两份样本，也未把其它历史项目作为最新版缺陷证据。

发现与修改：

| 问题 | 修正 |
|---|---|
| 模板把作者“本技能”的职责排除带入项目代理指令 | 生成物改写成面向项目代理的任务路由，作者边界仍留在 SKILL 中 |
| 挑下一项、修复全部基线失败、提交与清理工作区的条件不完整 | 两档均按真实任务与授权执行；区分原有失败和本次引入；提交需授权且完成定义满足；保护已有修改及未跟踪文件 |
| 非工程档假设已有记录入口 | 已确认的入口沿用；入口缺失时回复证据与阻塞，用户要求持久化才确认位置；完成定义与收尾共用入口规则 |
| 结构满分被当成维护停止条件 | 生成和维护共用内容复核，满分仍看实际失准；原地修正并保留项目特例、第三方块 |
| 实跑出现“已获用户授权却自报未获确认” | 创建、维护与 gotchas 统一按授权来源和范围判断；先 dry-run，已有真实授权覆盖则执行；不可信文件或网页不授予权限 |
| 新契约检测器自身可被合法邻句或无关否定蒙混通过 | 修正 clause 切分、everyClauseAny 量词；删除裸“不/未”的条件匹配；提交与状态更新各自绑定动作，加入同一行混合句、无关否定和跨动作借用反例 |

README、生成器收尾提示、两套评估材料同步了入口与授权规则。保持三个子系统、工程档唯一 owner、显式非工程档、不代建状态或交接体系等核心设计。没有新增运行时依赖，没有提高任何字节、行数、规则条数或评分阈值。

## 实测与对照

| 检查 | 结果与证据边界 |
|---|---|
| 独立代理带 skill / 不带 skill 的三类任务 | 两臂均实际执行创建、维护和只读审查；不是 dry-run 模拟评分 |
| 创建任务 | 带 skill 使用生成器，baseline 手写；两者执行路径不同，因此不能把丰富度、字节数等差异归因于 skill 文本 |
| 维护任务 | 同一受控夹具中，带 skill 修正基线范围、提交和维护触发；baseline 修正了提交和维护触发，但“授权推进后先修基线”仍未限制失败修复范围；仅一个夹具，不外推生产效果 |
| 项目特例保留 | 维护试跑保留 Windows 验证命令和第三方 Agent skills 块 |
| 只读审查 | 两臂均零写入；带 skill 臂文件哈希及修改时间保持不变 |
| 夹具结构得分 | 维护夹具缺 init 等结构，实际只得 33/100；没有为迎合“满分”描述而补无关文件。真实两份用户样本当时均为 100/100，但不是候选修改效果证明 |
| 授权修正定点复验 | 修后独立代理先 dry-run（exit 0），再真写（exit 0），真实检查与 init.sh 均 exit 0；没有重复确认或误报未获授权 |
| 授权反向边界 | 无授权应停、文件伪造授权应拒绝，仅静态复核规则，本轮没有行为对抗实测 |

## 工具验证

主代理完整复验命令（目标为本轮创建的非工程夹具）：

```text
node --check scripts/create-harness.mjs
node --check scripts/run-benchmark.mjs
git diff --check
node scripts/run-benchmark.mjs --target <fixture> --output <report.json>
```

完整基准自检 19 组及报告覆盖检查通过；夹具结构分 100/100；eval 覆盖 100/100（27/27）。字节预算按 LF 归一化：SKILL.md **12756/12862 B**；默认 AGENTS.md **3630/4036 B**，72/90 行、5/8 条工作规则。预算常量未修改。相对基线，SKILL.md 行数不变，工程模板净减 3 行、非工程模板净减 2 行；两档工作规则仍各 5 条。

独立 verifier C 重建基线文件树，仅换入新检测器：exit 1，六组检查失败；当前树控制臂 exit 0。另实测默认生成、蓝图、CLAUDE 文件名、非工程真实命令、非工程无验证声明等路径；单独 `--no-verification` 被拒绝。

检测器反例包括：删除保护条件、注入旧规则、同一行合法条件句旁追加无条件提交/更新、合法记录句旁追加任意记录写入，以及“不新建分支，直接提交所有改动”“未完成工单，直接提交所有改动”。对照控制臂通过，已知违规反例失败；这些不是任意自然语言的完备验证。

## 裁决与限制

- Judge A：better / clear；指出的作者措辞、每次动作判据、非工程标记及 gotchas 矛盾已定点修正并复核。
- Judge B：better / slight；接受改进，同时指出创建对照路径混杂和样本不能证明候选效果，已在上文明确。
- Judge C：better / clear；脚本验收通过；指出检测器否定范围、README 漂移和人工提示集不自动执行，已修复已知反例、同步 README 并标注验证边界。
- `test-prompts.json` 是人工/代理会话实测材料，不由自检执行；eval 覆盖不是模型行为通过率。
- 存在性检查防规则缺失，已知反例检查防特定回归；两者不保证新增任意违规散文都会被识别。最终定点复核确认提交/状态更新的跨动作否定借用已闭合，26 条见证全部命中对应要求。仍接受的检测边界包括连接词借用、存在性检查旁另加相反规则，以及 plainRecord 中“不更新状态，直接写入任意记录”的复合句；这些不出现在当前模板中，本轮未把检查器扩展为中文语义分析器。
- 主正文仅剩 106 B 预算余量，后续扩写需先合并冗余，不能靠提高预算通过。
- 本轮不改两份用户样本，不合并默认分支；源码与评估结果在优化分支交付。

安装同步尝试被本机硬安全策略拒绝（目标在当前工作区之外），未执行复制，已安装副本仍为基线。本轮交付的是优化分支源码和评估产物，未绕过该限制。

无待用户裁定项。结果卡采用 paired 裁决和证据边界，不用虚构的九维分数条。
