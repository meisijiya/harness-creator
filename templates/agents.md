## 启动工作流

编写代码前：

1. **确认工作目录**：运行 `pwd`
2. **完整阅读本文件**
3. **阅读 `CONTEXT.md`（如存在）**：统一领域语言与术语；它只承载代码表达不了的业务用语，不重复代码
4. **阅读最近的 ADR（如存在）**：了解 `docs/adr/` 中的关键决策背景
5. **阅读项目文档（如存在）**（`docs/ARCHITECTURE.md`、README 或等效文档）
6. **运行 `./init.sh`** 验证环境健康
7. **阅读 `feature_list.json` 与 `progress.md`**：查看当前功能状态、证据、阻塞与下一步
8. **阅读交接文档（如存在）**：`.scratch/handoff.md` 或会话约定的临时路径
9. **查看最近提交**：运行 `git log --oneline -5`

如果基线验证失败，先修复它，再添加新的工作范围。

## 工作规则

- **一次一个功能**：从 `feature_list.json`（或工单系统）中恰好挑选一个未完成的功能
- **依赖清晰**：功能间的依赖（dependencies / blocking 边）在 `feature_list.json` 或工单中显式声明，先决项未完成不动手
- **必须验证**：未运行验证命令前不得声称完成
- **证据先行**：完成证据（命令与结果摘要，或 CI 检查链接）记入 `feature_list.json` 的 `evidence` 与 `progress.md`
- **决策进 ADR**：架构与约定类决策写入 `docs/adr/`（如项目已建立），不写入 `progress.md`
- **保持在范围内**：不要修改与当前功能无关的文件
- **任务材料入 `.scratch/`**：spec 草稿、调研笔记等任务级材料放 `.scratch/`，任务完成即删除，不进默认上下文
- **产物落点唯一**：任何新引入的 skill/工具，其产物必须落在五个落点之一——`.scratch/`（临时）、`CONTEXT.md`（领域语言）、ADR（决策）、`init.sh`/CI（约束）、工单/状态文件（状态）。落不下的，拒绝引入
- **项目文档治理**：`design.md`、`docs/` 按需路由读取；其中可执行约束转门禁、术语进 `CONTEXT.md`、决策进 ADR、过时归档；与代码重复视为双写
- **留下干净状态**：下次会话必须能立即运行 `./init.sh`

## 必需产物

- `feature_list.json` —— 功能状态与证据的事实来源
- `progress.md` —— 精简日志：当前状态、完成证据、阻塞、下一步
- `init.sh` —— 标准启动与验证路径
- `CONTEXT.md` + ADR —— 可选长期资产：领域语言与决策史
- `.scratch/` —— 可选任务级暂存区：spec 草稿与交接文档，随任务删除

## 完成定义

只有同时满足以下所有条件，功能才算完成：

- [ ] 目标行为已实现
- [ ] 要求的验证确实运行过（测试 / lint / 类型检查）
- [ ] 证据已记录在 `feature_list.json` 的 `evidence` 与 `progress.md` 中
- [ ] 仓库仍可从标准启动路径重新启动

## 会话结束

结束会话前：

1. 更新 `progress.md`：当前状态、完成证据、阻塞、下一步（不写决策与文件清单——决策进 ADR，文件见 git）
2. 用新的功能状态与证据更新 `feature_list.json`
3. 如需跨会话交接：写**引用式交接文档**到 `.scratch/handoff.md`（或操作系统临时目录）。只写增量信息——目标、当前状态、推荐的下一步；用路径或 URL 引用 spec、ADR、提交与 diff，不复制其内容
4. 记录任何未解决的风险或阻塞
5. 工作处于安全状态后，用描述性消息提交
6. 让仓库保持足够干净，下次会话能立即运行 `./init.sh`

## 升级处理

如果你遇到：
- **架构决策**：查阅 ADR 与项目架构文档（如存在），否则询问用户；定论后写入 ADR
- **需求不清**：查阅产品/需求文档与 `CONTEXT.md`（如存在），否则询问用户

- **范围模糊**：重新阅读 `feature_list.json` 中的完成定义
