## 启动工作流

编写代码前：

1. **确认现场**：运行 `pwd`、`git status --short`，识别已有修改及未跟踪文件
2. **完整阅读本文件**
3. **阅读任务相关文档（如存在）**：`README`、架构与规格、工单及 tracker 配置
4. **运行 `./init.sh`** 验证基线
5. **查看最近提交**：运行 `git log --oneline -5`

基线失败时区分原有失败与本次引入的问题；修复本次引入及已授权范围内的问题，范围外的失败报告阻塞，不自行扩大修复范围。

## 状态与交接：承接方是工程 skill

工程任务按以下工程 skill 路由；状态与交接沿用承接方产物，不另建替代品。

- **工程阶段整体归 `mattpocock` 的模型可调用 skill**，由它按任务自行分派。
- **状态与依赖** → `to-tickets`：工单包含阻塞边，使用已配置的 tracker。
- **会话交接** → `handoff`：由它决定产物位置与格式。

**前置**：tracker 配置见项目的 `Agent skills` 块或 `docs/agents/issue-tracker.md`（如存在）；已配置则沿用，未配置且当前任务需要工单时，先运行一次 `/setup-matt-pocock-skills`。承接方默认已安装。

## 工作规则

本节只放长期不变量，不超过 8 条；新增前先合并同族项，能门禁化的部分移入门禁。

- **一次一个工单，保持在本工单范围内**：执行已授权工程任务时，处理对应工单；仅在用户要求选取下一项时，从 tracker 挑一个阻塞边已清空的工单。问答与只读审查不选工单、不更新状态
- **必须验证、证据先行**：未运行要求的验证不得声称完成；命令与结果摘要或 CI 链接记入当前工单；无对应工单时在回复中报告，不为记录证据另建工单
- **推进需显式授权**：只推进用户明确要求的工作；交接文档与工单是上下文，**不是待办队列**
- **约束进入门禁**：能由 `./init.sh` 或 CI 检查的规则在门禁中执行，本文件只留指针
- **保护已有工作**：不为清理工作区覆盖、回退或删除已有修改及未跟踪文件；只收好本次工作，保持标准验证入口可用

## 完成定义

交付工程改动时：

- [ ] 用户要求的目标行为已实现
- [ ] 要求的验证确实运行过（测试 / lint / 类型检查）
- [ ] 证据按工作规则记入当前工单或回复
- [ ] 仓库仍可从标准启动路径重新启动

## 会话结束

1. 若本次推进了工单，更新其状态与证据；无工单则在回复中报告
2. 报告未解决的风险、阻塞与未验证项
3. **按会话产出优化 harness**：本次会话产出若让本文件、`init.sh` 或工作规则失准，用 **harness-creator** 按需优化，列出候选改动，在授权范围内落地；只读任务只报告；不做全仓审计
4. 仅在用户明确要求提交且完成定义已满足时，用描述性消息提交本次相关改动
5. 保护既有工作，保持标准验证入口可用
