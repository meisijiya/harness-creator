# 验证与证据细则

> **按需读**，不是常驻指令文件：只在「这条验证到底证明了什么」「证据记到哪、够不够」有疑问时
> 打开。启动工作流里没有要求每次会话都读它。

本文件解释判据与处置动作。**规则本身在 `AGENTS.md` 的工作规则节**，这里不新增约束，只说明
「为什么这样判」和「遇到判不出来的情况怎么办」。

## 证据要锚到版本，不只是「记下来」

一条证据回答两个问题：**跑了什么**（命令与结果摘要），以及**跑的是哪一版**（commit）。

缺了第二个，证据记录在一周后读起来与今天写下的完全一样——都写着「测试通过」，但可能对应着
不同的代码。`./init.sh` 在成功尾部打印 `Evidence anchor: <短哈希>`，那个哈希就是「这些检查
跑在哪个提交上」的机械答案。记证据时把它一起记下。

仓库没有提交时 `./init.sh` 会拒绝运行并给出修复命令。没有提交就没有锚点，而「HEAD」在每一条
记录里都是同一个字符串——那正是锚点要区分的东西。

## 出处：主张要有可查的来源

`references/` 下每份 pattern 文档的关键机制主张都带 `（来源：标题，URL）`。这不是装饰：

- **出处让主张可被证伪**。一条没有出处的规则，读者只能选择信或不信；一条有出处的规则，读者
  可以去读原文并判断它在本项目是否成立。
- **出处让腐烂可被机械发现**。`node scripts/check-links.mjs` 校验仓内 Markdown 的相对链接锚点
  是否指向真实存在的标题。锚点腐烂时没有任何东西会失败——文档只是悄悄指了个空处，而门禁能
  在它发生时报出来。

该脚本**只校验锚点、不校验网络可达性**：超时与页面删除从本地看一样，本仓无权判定后者。网络
不可达降级为提示，退出码仍是 0；只有格式非法或相对锚点确实不存在才 exit 1。

## 「定义了但没接线」是发现，不是本仓的缺陷

`node scripts/validate-harness.mjs` 会报出 `N defined but not wired: npm run lint` 这类结果：
项目在 `package.json` 里定义了 `lint`，而 `init.sh` 从头到尾没提它。

**这不会让审计失败**，因为它反映的是目标项目自己的选择，不是本技能产物的缺陷。但它必须被
看见，原因是门禁的结构：`has_script "lint"` 守卫在脚本缺失时 SKIP 并继续走，只要还有**任何**
一条检查真跑过，`RAN` 计数就成立，`./init.sh` 打印成功尾部并 exit 0。于是一个从未跑过 lint 的
项目，看起来和一个 lint 通过的项目没有区别。

处置：

- 该跑 lint → 走 `--add-check "npm run lint"`，它会实跑门禁并在缺横幅或非零时字节级回滚。
- 不该跑 → 从 `package.json` 删掉这个脚本定义。一条定义了却永不执行的检查，比没有这条检查更
  危险：它让人以为它被覆盖了。
- 用别的工具跑 lint → 在 `init.sh` 里显式写那一步，不要靠 `package.json` 的名字。

## 怎么维护这一份

用户陈述变了才改。「待补」变成有据可依的事实时，把依据补进上面那一节；依据消失（文件删了）
时，把它退回「待补」，不要留着一条已经过期的断言。
